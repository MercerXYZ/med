# KRGen: устройство и принятые решения

Каждое утверждение КР прослеживается по цепочке:

```
PDF → страница и дословная цитата → проверенный факт → группа фактов → решение по противоречию → тезис или абзац КР → Word / JSON
```

## 1. Этапы

| Этап | Модуль | Запросов к модели | Что делает |
|---|---|---|---|
| загрузка | `pdf_ingest.py` | — | текст по страницам, SHA-256 и «отпечаток» текста для дубликатов, разметка страниц: основной текст, список литературы, нет текста |
| keywords | `extract.py` | 1 на проект | термины темы для выбора страниц длинных документов |
| extract | `extract.py`, `pdf_ingest.py` | 1 на документ (библиография) + 1 на фрагмент | дизайн исследования, DOI, дубликаты по DOI и названию, выбор страниц, фрагменты по 1–3 страницы, факты |
| verify | `verify.py` | 1 на 15 фактов | проверки кодом, затем рецензент |
| group | `groups.py` | 1 на 45 фактов раздела; ещё 1 на 70 групп, если раздел шёл в несколько запросов | группы фактов и противоречия |
| resolve | `resolve.py` | — | нормирование противоречий по правилам |
| kr | `synth.py` | 1 на 6 групп (разделы 2–6); 1 на 40 фактов описательного раздела | тезисы и абзацы, УДД, УУР |
| снимок | `snapshots.py` | — | Word, Markdown, JSON и сводка прогона в `data/snapshots/<прогон>/` |

Этапы идут по порядку, каждый сразу пишет результат в SQLite. Если прогон оборвался, повторный
запуск доделывает недостающее: готовые фрагменты помечены, ответы модели лежат в кэше.

## 2. Факты с дословными цитатами

Модель не пишет КР по статьям сразу. Сначала она выписывает отдельные факты, причём сначала копирует
цитату и номер страницы, а уже потом формулирует утверждение по-русски. Так у каждого факта есть
проверяемая опора: цитату можно найти в тексте PDF кодом, показать эксперту на изображении страницы
и сослаться на неё в КР. Пересказ модели такой проверки не даёт.

Поля факта (раздел КР, тип утверждения, направление, группа пациентов, возраст, вмешательство,
доза, сроки, пороги, условия, связь с темой, пересказ чужой работы) нужны дальше: по ним идут
группировка, правила для противоречий и расчёт УДД.

DOI принимается, только если он есть в тексте PDF. Дубликат определяется дважды: при загрузке (тот
же текст первых страниц; тот же файл повторно не добавляется) и после библиографии (тот же DOI или
название). Иначе одна статья в двух вёрстках считалась бы двумя источниками и завышала УУР.

## 3. Двухуровневая проверка

**Уровень 1 — код.** Цитата ищется на заявленной странице, затем на остальных и на стыке соседних
страниц. Перед сравнением текст нормализуется (`textnorm.norm_hard`): NFKC, лигатуры, единые тире и
кавычки, нижний регистр, удаление пробелов и дефисов. Пробелы удаляются целиком, потому что в PDF с
выравниванием по ширине они расставлены произвольно. Совпадение подстрокой — «дословно»; сходство
от 90% — «после нормализации»; от 75% — частично (на проверку); ниже — не найдена.

Нестрогое совпадение может пропустить искажение, поэтому цитата дополнительно сверяется посимвольно
с тем местом страницы, куда она легла: цифры, десятичная точка, минус, пары «знак + число +
единица» (mg/mcg, %, <, >), количество отрицаний, антонимы (significant / non-significant, increased /
decreased). Известные дефекты текстового слоя (минус, закодированный как «2», «=» как «¼», ошибки
OCR) не считаются искажением: такой факт уходит на проверку с пометкой сверить по изображению.

**Уровень 2 — рецензент.** Отдельный промпт с задачей искать ошибки, окно текста около 1000 символов
вокруг цитаты и описание исследования. Рецензент отвечает, подтверждает ли цитата формулировку
(`supported`, `partial`, `not_supported`), и отдельно — верны ли числа, отрицание, группа пациентов
и тип утверждения. Он ловит то, что строкой не проверить: результат исследования выдан за
рекомендацию, данные по взрослым перенесены на всех.

**Итоговый статус** (`verify._status`):

- ошибка уровня 1 (цитата не найдена, цифра изменена) — `unverified`;
- рецензент не ответил — `needs_review`;
- рецензент ответил `not_supported` — `unverified`;
- `partial`, замечания рецензента или сомнения уровня 1 — `needs_review`. Часть сомнений (числа
  есть рядом с цитатой, но не в ней; расхождение отрицаний; нет рекомендательной формулировки)
  рецензент может снять;
- иначе `verified`.

Почему так, а не иначе:

| Вариант | Почему не выбран |
|---|---|
| спросить ту же модель, уверена ли она | модель склонна подтверждать собственные ошибки и не проверяет наличие цитаты |
| только поиск цитаты | цитата может быть настоящей, но не подтверждать формулировку |
| только рецензент | рецензент тоже ошибается, а числа, единицы и отрицания код проверяет надёжно и бесплатно |
| ручная проверка всего | сотни фактов на тему; эксперту стоит смотреть только спорные |

## 4. Группировка до КР

Разные статьи часто утверждают одно и то же. Если писать тезисы по отдельным фактам, в КР получаются
повторы, а склеивать готовые тезисы потом сложнее и рискованнее. Поэтому факты группируются до КР:
одна группа фактов — один тезис, все факты группы — его доказательства.

- В группы идут только живые факты (`groups.live_facts`): подтверждённые проверкой или экспертом,
  не отклонённые, не из дубликатов, по теме.
- Группировка идёт внутри раздела КР пачками по 45 фактов. Если пачек несколько, второй запрос
  сводит одинаковые группы из разных пачек.
- Модель предлагает группы и противоречия, код проверяет: в одной группе не могут быть дети и
  взрослые, а также противоположные выводы. Такая группа делится детерминированно. Факты, которые
  модель потеряла, становятся отдельными группами.
- Id группы — хэш её фактов, id тезиса — хэш id группы. Правка эксперта (формулировка, «не включать
  в КР») переносится на новую группу, если та содержит не меньше половины фактов старой.
- При сбое модели прежние группы раздела сохраняются.

## 5. Нормирование противоречий по правилам

Решение «какая сторона права» принимает код (`resolve.decide`), а не модель: правила одинаковы при
каждом запуске, каждое решение объясняется одной строкой, а сила стороны меряется тем же УДД по
приложению А2, что и в тезисах. Модель только находит противоречия и описывает, в чём расхождение.

Правила по порядку:

1. У одной из сторон не осталось живых фактов — оставить оба.
2. Стороны про разные группы пациентов (дети и взрослые) — оставить оба.
3. Разные числа в описательном разделе (1.1–1.6, 7) — оставить оба, в тексте приводятся обе оценки.
4. УДД сторон различается — выигрывает сторона с лучшим (меньшим) УДД; сторона без УДД проигрывает.
5. УДД равен, а число независимых источников различается хотя бы на 2 — выигрывает сторона с
   большим числом источников.
6. Иначе решения нет, противоречие ждёт эксперта.

Эксперт может выбрать любое из четырёх решений, и оно больше не пересчитывается. В КР не идут факты
проигравшей стороны, обе стороны при «Исключить оба» и обе стороны нерешённого противоречия.
Последнее сделано намеренно: спорное утверждение не должно попасть в КР, пока его не разобрали.

## 6. КР по приказу 103н

- Структура: титул, разделы 1 (1.1–1.6), 2 (2.1–2.5), 3 (3.1–3.3), 4, 5, 6, 7, критерии оценки
  качества, список литературы, приложение А2 со шкалами УДД и УУР. Подраздел без содержимого не
  выводится, пустой раздел верхнего уровня получает строку «Нет данных в загруженных источниках.».
  Служебных примечаний в документе нет.
- Разделы 2–6: тезис на группу с вводной фразой «Рекомендуется / Не рекомендуется …». Группа,
  где все факты справочные, тезиса не даёт.
- Разделы 1.x и 7: связный текст со ссылками на источники, без УДД и УУР.
- В запрос на группу идут её формулировка и до 12 фактов (по одному на источник, сильные первыми),
  доказательствами тезиса остаются все факты группы.
- Список литературы — по документам, на которые ссылаются вошедшие в КР факты.

## 7. УДД и УУР считает код

- **УДД** — по дизайну источника и таблицам 1–2 приложения А2 (для диагностики и для лечения
  разные шкалы). Систематический обзор без метаанализа — УДД 2. Пересказ чужой работы УДД статьи
  не получает. Если УДД определить нельзя (дизайн неизвестен, источник — руководство), в окне 4
  стоит пометка «УДД не определён», а в документе — УДД 5 и УУР C.
- **Независимый источник** — публикация (DOI или название), а не файл.
- **УУР** (`synth.preliminary_uur`): A — все источники УДД 1–2 и либо есть УДД 1, либо источников
  не меньше двух; B — лучший УДД 1–3, но условия A не выполнены; C — УДД 4–5. Если все факты,
  давшие УДД, косвенные или популяция в тезисе шире, чем в фактах, A понижается до B.
- **Вводная фраза**: «Рекомендуется» / «Не рекомендуется» при УУР A–B или явной рекомендации в
  источнике, иначе «Рекомендуется рассмотреть возможность» / «Не рекомендуется рассматривать».
- Числа в тексте тезиса, которых нет в цитатах, дают пометку «Числа не найдены в цитатах».
  Комментарий с такими числами в КР не берётся.

## 8. Правки эксперта не теряются

- У фактов и тезисов два слоя: `auto` (результат программы) и `override` (правки эксперта).
  Повторная обработка пишет только в `auto`. Если новый вариант отличается, а правка уже есть, он
  кладётся в `pending_auto`, и эксперт выбирает «Принять новую» или «Оставить мою».
- Если при повторном извлечении изменилось содержимое подтверждённого факта, подтверждение
  снимается: эксперт подтверждал прежний текст.
- Решение по противоречию хранится по id (хэш сторон) и сохраняется при повторной группировке.
- Правленый, утверждённый или отклонённый тезис при сдвиге состава группы привязывается к новому
  тезису с наибольшим числом общих фактов. Если нового тезиса нет, правленый остаётся
  «осиротевшим» и в КР выводится, только если утверждён.
- Все действия пишутся в журнал `expert_edits`. КР считается устаревшей (`projects.kr_is_stale`),
  если после последней сборки (`projects.meta.kr_built_at`) эксперт менял факты, группы или решения
  по противоречиям или если какой-то живой факт ещё не попал в группу.

## 9. Модель и кэш

- `claude-haiku-5-5` через Claude Agent SDK на подписке Claude: `ANTHROPIC_API_KEY` удаляется из
  окружения, инструменты агента выключены, ответ — JSON по схеме, уровень рассуждений `low`.
- Каждый ответ проверяется по JSON-схеме до записи в кэш. Ключ кэша — модель, этап, уровень
  рассуждений, версия промпта, текст запроса и схема. Повтор тех же данных бесплатен, смена промпта
  даёт новый результат.
- Ошибка модели не превращается в «фактов нет»: фрагмент получает статус ошибки, страницы — причину,
  документ — «частично». Прогон, прерванный остановкой сервера, при следующем старте помечается
  остановленным.
- Стоимость в отчётах — эквивалент по ценам API, который сообщает SDK; фактически расходуются лимиты
  подписки.

## 10. Хранение

SQLite `data/krgen.sqlite`. Таблицы: `projects`, `documents`, `pages`, `chunks` (фрагменты),
`cards` (факты), `clusters` (группы), `conflicts`, `theses`, `expert_edits`, `llm_calls` (каждый
запрос с токенами и стоимостью), `runs` (прогоны). Миграции добавляют колонки и ничего не удаляют,
старые базы открываются без потерь.

## 11. Ограничения

- OCR нет: страницы без текстового слоя помечаются и не обрабатываются.
- Таблицы и рисунки читаются только как текст PDF; числа из таблиц модель часто цитирует неточно,
  такие факты уходят на проверку.
- Длинные документы: обрабатываются не больше 60 страниц, отобранных по ключевым словам темы,
  остальные помечаются пропущенными.
- Дизайн исследования определяет модель по первым страницам; ошибка дизайна даёт ошибку УДД.
- Противоречия ищутся только внутри раздела КР.
- Факты «на проверке» в группы не идут, пока их не подтвердит эксперт; при большом числе таких
  фактов КР получается неполной.
- Рецензент — та же модель, что и при извлечении, поэтому возможны согласованные ошибки. Проверки
  кодом это частично компенсируют.
