# KRGen: устройство и принятые решения

Каждое утверждение КР прослеживается по цепочке:

```
PDF → страница и дословная цитата → проверенное доказательство → группа → решение по противоречию → тезис или абзац КР → Word / JSON
```

## 1. Онтология предметной области

`kr_recommendation.schema.json` описывает предметную область: метаданные КР (`kr_meta`),
доказательство из статьи (`evidence_unit` с источником `source`), тезис-рекомендацию
(`recommendation_thesis` с `intervention`, `consensus`, `quality_criterion`) и перечисления
(разделы 103н, дизайны исследований, типы вмешательств, УДД, УУР).

Программа работает по этой модели, а не выгружает в неё готовый результат. Модуль `ontology.py`
читает схему и отдаёт её части:

- в системный промпт каждого этапа — ровно ту часть схемы, с которой этап работает, вместе с
  описаниями полей и ограничениями;
- в схему ответа модели — поля с типами и перечислениями из онтологии, поэтому модель не может
  вернуть, например, дизайн исследования или раздел, которых нет в схеме.

| Этап | Часть онтологии в промпте | Что модель заполняет |
|---|---|---|
| описание источника | `source` | название, авторы, год, журнал, DOI, `study_design`, размер выборки, популяция |
| извлечение | `evidence_unit` | триплет `subject` / `predicate` / `object`, `negation`, `intervention_type` и цитата |
| рецензент | `evidence_unit` | сверяет формулировку и триплет с цитатой |
| раздел КР | `kr_section_enum` | раздел 103н для доказательства |
| группировка | `consensus` | группы и противоречия (`agreement = conflicting`) |
| тезисы | `recommendation_thesis` | `direction`, `intervention`, `evidence_backed_core`, `expert_additions`, `quality_criterion` |

Поля, которые по онтологии выводятся правилами, считает код: `udd`, `uur`, `strength_phrase` (из пары
`direction` и `uur`), `scale_ref` (из типа вмешательства), `consensus`, `evidence_refs`,
`auto_eligible` у критерия качества. Ограничения схемы соблюдаются в коде: противоречивые
доказательства не дают УУР A, `strength_phrase` согласована с `direction`.

## 2. Этапы

| Этап | Модуль | Запросов к модели | Что делает |
|---|---|---|---|
| загрузка | `pdf_ingest.py` | — | текст по страницам, SHA-256 и «отпечаток» текста для дубликатов, разметка страниц |
| keywords | `extract.py` | 1 на проект | термины темы для выбора страниц длинных документов |
| extract | `extract.py` | 1 на документ (источник) + 1 на фрагмент | дизайн исследования, DOI, дубликаты, фрагменты по 1–3 страницы, доказательства |
| verify | `verify.py` | 1 на 15 доказательств | проверки кодом, затем рецензент |
| classify | `classify.py` | 1 на 40 доказательств документа | раздел КР или «Категория не определена» |
| group | `groups.py` | 1 на 45 доказательств раздела; ещё 1 на 70 групп, если запросов было несколько | группы и противоречия |
| resolve | `resolve.py` | — | нормирование противоречий по правилам |
| kr | `synth.py`, `grading.py` | 1 на 6 групп (разделы 2–6); 1 на 40 доказательств описательного раздела | тезисы и абзацы, УДД, УУР |
| снимок | `snapshots.py` | — | Word, Markdown, JSON и сводка прогона в `data/snapshots/<прогон>/` |

Этапы идут по порядку, каждый сразу пишет результат в SQLite. Если прогон оборвался, повторный
запуск доделывает недостающее: готовые фрагменты помечены, ответы модели лежат в кэше.

## 3. Доказательства с дословными цитатами

Модель не пишет КР по статьям сразу. Сначала она выписывает отдельные доказательства, причём сначала
копирует цитату и номер страницы, а уже потом заполняет остальное. У каждого доказательства есть
проверяемая опора: цитату можно найти в тексте PDF кодом, показать эксперту на изображении страницы
и сослаться на неё в КР.

Поля доказательства — `evidence_unit` онтологии (триплет, отрицание, тип вмешательства) и
расширения, которые схема допускает: русская формулировка, цитата, страница, группа пациентов,
возраст, доза, сроки, условия, связь с темой, пересказ чужой работы. По ним идут проверка,
группировка, правила для противоречий и расчёт УДД.

DOI принимается, только если он есть в тексте PDF. Дубликат определяется дважды: при загрузке (тот
же текст первых страниц) и после описания источника (тот же DOI или название). Иначе одна статья в
двух вёрстках считалась бы двумя источниками и завышала УУР.

## 4. Двухуровневая проверка

**Уровень 1 — код.** Цитата ищется на указанной странице, затем на остальных и на стыке соседних
страниц. Перед сравнением текст нормализуется (`textnorm.norm_hard`): NFKC, единые тире и кавычки,
нижний регистр, без пробелов и дефисов (в PDF с выравниванием по ширине пробелы расставлены
произвольно). Совпадение подстрокой — «дословно»; сходство от 90% — найдена; от 75% — частично;
ниже — не найдена. Дальше код проверяет, что числа формулировки есть в цитате и что отрицание в
цитате, формулировке и поле `negation` согласовано.

**Уровень 2 — рецензент.** Отдельный промпт с задачей искать ошибки, текст около цитаты и описание
исследования. Рецензент отвечает, подтверждает ли цитата формулировку (`supported`, `partial`,
`not_supported`), и отдельно — верны ли числа, отрицание и группа пациентов.

**Итоговый статус** (`verify.status_for`):

- цитата не найдена — `unverified`;
- рецензент не ответил — `needs_review`;
- рецензент ответил `not_supported` — `unverified`;
- `partial`, замечания рецензента или замечания кода — `needs_review`. Замечания по числам и
  отрицанию рецензент может снять, если сам их проверил;
- иначе `verified`.

| Вариант | Почему не выбран |
|---|---|
| спросить ту же модель, уверена ли она | модель склонна подтверждать собственные ошибки и не проверяет наличие цитаты |
| только поиск цитаты | цитата может быть настоящей, но не подтверждать формулировку |
| только рецензент | рецензент тоже ошибается, а наличие цитаты и чисел код проверяет надёжно и бесплатно |
| ручная проверка всего | сотни доказательств на тему; эксперту стоит смотреть только спорные |

## 5. Раздел КР — отдельным запросом

Модель, которая извлекает доказательства, видит только фрагмент статьи и занята цитатой, поэтому
раздел определяется отдельным запросом (`classify.py`): тема КР, коды МКБ-10, возрастная группа,
описание каждого раздела 103н и перечисление `kr_section_enum` из онтологии. Доказательства идут
пачками по 40 внутри документа, поэтому новая статья не сбивает кэш ответов по уже обработанным.

Если доказательство не подходит ни к одному разделу, оно получает «Категория не определена»: остаётся
в окне «Факты» и отдельным списком в окне групп, но в группы и в КР не идёт. Раздел, заданный
экспертом, важнее раздела от классификации.

## 6. Группировка до КР

Разные статьи часто утверждают одно и то же. Поэтому доказательства группируются до КР: одна группа —
один тезис, все доказательства группы — его `evidence_refs`.

- В группы идут только подтверждённые доказательства (`groups.live_facts`): прошли проверку или
  подтверждены экспертом, не из дубликатов, по теме, с разделом.
- Группировка идёт внутри раздела пачками по 45. Если пачек несколько, второй запрос сводит
  одинаковые группы из разных пачек.
- Код проверяет ответ модели: в одной группе не бывает детей вместе со взрослыми и доказательств с
  разным `negation`. Такая группа делится. Доказательства, которые модель потеряла, становятся
  отдельными группами.
- Id группы — хэш её доказательств, id тезиса — хэш id группы. Если в новой группе осталась хотя бы
  половина доказательств старой, она получает прежний id: тезис, его статус и правки эксперта
  остаются на месте.
- При сбое модели прежние группы раздела сохраняются.

## 7. Нормирование противоречий по правилам

Решение «какая сторона права» принимает код (`resolve.decide`), а не модель: правила одинаковы при
каждом запуске, каждое решение объясняется одной строкой. Модель только находит противоречия.

1. У одной из сторон не осталось подтверждённых доказательств — оставить оба.
2. Стороны про разные группы пациентов (дети и взрослые) — оставить оба.
3. Разные числа в описательном разделе (1.1–1.6, 7) — оставить оба, в тексте приводятся обе оценки.
4. УДД сторон различается — выигрывает сторона с лучшим (меньшим) УДД.
5. УДД равен, а число независимых источников различается хотя бы на 2 — выигрывает сторона с
   большим числом источников.
6. Иначе решения нет, противоречие ждёт эксперта.

В КР не идут доказательства проигравшей стороны, обе стороны при «Исключить оба» и обе стороны
нерешённого противоречия. Если эксперт оставил обе стороны настоящего противоречия, у тезиса
`consensus.agreement = conflicting`, и по правилу онтологии УУР не бывает выше B.

## 8. КР по приказу 103н

- Структура: титул, разделы 1 (1.1–1.6), 2 (2.1–2.5), 3 (3.1–3.3), 4, 5, 6, 7, критерии оценки
  качества, список литературы, приложение А2 со шкалами УДД и УУР. Пустой подраздел не выводится,
  пустой раздел верхнего уровня получает строку «Нет данных в загруженных источниках.».
- Разделы 2–6: тезис на группу с вводной фразой «Рекомендуется / Не рекомендуется …».
- Разделы 1.x и 7: связный текст со ссылками на источники, без УДД и УУР.
- В запрос на группу идут её формулировка и до 12 доказательств (по одному на источник, сильные
  первыми), в `evidence_refs` остаются все.
- Список литературы — по документам, на которые ссылаются вошедшие в КР доказательства.

## 9. УДД и УУР считает код (`grading.py`)

- **УДД** — по `study_design` источника и таблицам 1–2 Приложения А2. Шкала (`scale_ref`)
  выбирается по типу вмешательства, как в онтологии: диагностика — `udd_diagnostic`, остальное —
  `udd_treatment`. Пересказ чужой работы УДД статьи не получает. Если УДД определить нельзя, в окне
  КР стоит пометка «УДД не определён», а в документе — УДД 5 и УУР C.
- **Независимый источник** — публикация (DOI или название), а не файл.
- **УУР** (`preliminary_uur`): A — все источники УДД 1–2, выводы согласованы и либо есть УДД 1, либо
  источников не меньше двух; B — лучший УДД 1–3, но условия A не выполнены; C — УДД 4–5. Если все
  доказательства, давшие УДД, косвенные, A понижается до B.
- **Вводная фраза** выводится из пары (`direction`, `uur`): УУР A–B — «Рекомендуется» / «Не
  рекомендуется», иначе «Рекомендуется рассмотреть возможность» / «Не рекомендуется рассматривать».
- Число в тексте тезиса, которого нет в цитатах, попадает в `expert_additions` с
  `basis = expert_consensus` и даёт пометку «Числа не найдены в цитатах».

## 10. Правки эксперта не теряются

- У доказательств и тезисов два слоя: `auto` (результат программы) и `override` (правки эксперта).
  Повторная обработка пишет только в `auto`. Если новый вариант отличается, а правка уже есть, он
  кладётся в `pending_auto`, и эксперт выбирает «Принять новую» или «Оставить мою».
- Если при повторном извлечении изменилось подтверждённое доказательство, подтверждение снимается.
- Решение эксперта по противоречию сохраняется при повторной группировке.
- Все действия пишутся в журнал `expert_edits`. КР считается устаревшей (`projects.kr_is_stale`),
  если после последней сборки эксперт менял доказательства, группы или решения по противоречиям или
  если подтверждённое доказательство ещё не попало в группу.

## 11. Модель и кэш

- `claude-haiku-5-5` через Claude Agent SDK на подписке Claude: `ANTHROPIC_API_KEY` удаляется из
  окружения, инструменты агента выключены, ответ — JSON по схеме, уровень рассуждений `low`.
- Каждый ответ проверяется по схеме до записи в кэш. Ключ кэша — модель, уровень рассуждений, этап,
  текст промпта и схема. Повтор тех же данных бесплатен, смена промпта даёт новый результат.
- Ошибка модели не превращается в «доказательств нет»: фрагмент получает статус ошибки, документ —
  «частично». Прогон, прерванный остановкой сервера, при следующем старте помечается остановленным.
- Стоимость в отчётах — эквивалент по ценам API, который сообщает SDK; фактически расходуются лимиты
  подписки.

## 12. Хранение

SQLite `data/krgen.sqlite`. Таблицы: `projects`, `documents`, `pages`, `chunks` (фрагменты),
`cards` (доказательства), `fact_groups` (группы), `conflicts`, `theses`, `expert_edits`,
`llm_calls` (каждый запрос с токенами и стоимостью), `runs` (прогоны).

## 13. Ограничения

- OCR нет: страницы без текстового слоя помечаются и не обрабатываются.
- Таблицы и рисунки читаются только как текст PDF; числа из таблиц модель часто цитирует неточно,
  такие доказательства уходят на проверку.
- Длинные документы: обрабатываются не больше 60 страниц, отобранных по ключевым словам темы.
- Дизайн исследования определяет модель по первым страницам; ошибка дизайна даёт ошибку УДД.
- Противоречия ищутся только внутри раздела КР.
- Доказательства «на проверке» в группы не идут, пока их не подтвердит эксперт.
- Рецензент — та же модель, что и при извлечении, поэтому возможны согласованные ошибки.
