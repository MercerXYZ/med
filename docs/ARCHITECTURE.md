# KRGen — архитектура и обоснование решений

Система формирует **черновик** клинической рекомендации (КР) по структуре приказа Минздрава России
№ 103н из пакета научных статей. Каждое утверждение черновика прослеживается по цепочке

```
PDF → страница + дословная цитата → карточка доказательства (проверенная) → тезис → Word/JSON
```

Результат — материал для эксперта, а не готовая КР: цитата подтверждает происхождение текста,
но не его клиническую правильность.

## 1. Конвейер

| Этап | Модуль | LLM | Что делает |
|---|---|---|---|
| Загрузка | `pdf_ingest.py` | — | SHA-256 и отпечаток текста (дубликаты: одна статья под разными именами), текст по страницам, разметка страниц: тело / список литературы / без текстового слоя |
| Ключевые слова темы | `extract.py` | 1 вызов | Термины темы (рус./англ.) для ранжирования страниц длинных документов |
| План страниц | `pdf_ingest.py` | — | Короткие документы — целиком; длинные (книги, руководства) — топ-N релевантных страниц, остальное **явно** помечается пропуском |
| Библиография | `extract.py` | 1 на документ | Название, авторы, год, журнал, дизайн исследования. DOI проверяется регуляркой по тексту — DOI «из памяти» отбрасывается |
| Извлечение | `extract.py` | 1 на фрагмент | Фрагменты по 1–3 страницы с маркерами `[[PAGE N]]`; модель сначала копирует цитату, потом формулирует утверждение (quote-first) |
| Верификация | `verify.py` | 1 на 15 карточек | Уровень 1 — детерминированные проверки, уровень 2 — LLM-рецензент |
| Повторы и противоречия | `cluster.py` | 1 на 45 карточек раздела КР | LLM предлагает кластеры/дубликаты/конфликты, код запрещает опасные слияния |
| Тезисы | `synth.py` | 1 на 6 кластеров; 1 на описательный раздел | Формулировка тезиса; УДД, УУР, вводная фраза, проверка чисел и популяции — кодом |
| Объединение тезисов | `merge.py` | 1 на раздел | Повторы тезисов из разных пакетов → один тезис с объединёнными доказательствами; уровни пересчитываются |
| Снимок | `snapshots.py` | — | Неизменяемый снимок результата прогона (JSON, Markdown, Word, сводка) для истории |
| Экспорт | `export.py` | — | JSON (своя схема + схема `kr_recommendation`), Markdown, Word |

Все этапы идемпотентны и сохраняют результат сразу (SQLite). Сбой API не теряет полученное;
повторный запуск дообрабатывает недостающее (кэш ответов + статусы фрагментов).

## 2. Почему такой подход к верификации

Исходная проблема: качество автоматически написанных КР у многих авторов не превышает 40%,
а ошибка в медицинском тексте может навредить пациенту. Самые опасные ошибки LLM в этой задаче:

1. **Выдуманная или «отредактированная» цитата** (модель пересказывает, а не копирует).
2. **Искажённое число** — доза, порог, срок.
3. **Потерянное или добавленное отрицание** («не уступает» → «лучше», «нет различий» → «эффективно»).
4. **Результат исследования, выданный за рекомендацию авторов.**
5. **Расширение популяции** (данные по взрослым → «всем пациентам», дети ↔ взрослые).
6. **Слияние разных утверждений** (разные дозы/возрасты) и **молчаливый выбор** одной из противоречащих версий.

Мы выбрали **многоуровневую верификацию с разделением ролей**, потому что:

* **Детерминированные проверки нельзя «уговорить».** Цитата либо есть на странице после
  оговорённой нормализации, либо нет. Числа формулировки либо есть в цитате, либо нет. Это ловит
  ошибки 1–3 без стоимости и без ложной уверенности. Альтернатива «спросить ту же модель, уверена ли
  она» (self-check) систематически подтверждает собственные ошибки.
* **LLM-рецензент — отдельная роль**: другой промпт («найди ошибки, при сомнении — partial»),
  расширенный контекст вокруг цитаты (окно ~1000 символов) и описание исследования, без доступа к
  рассуждениям генератора. Он ловит смысловые ошибки 4–5, которые строкой не проверить.
* **Код, а не модель, принимает решения, которые можно формализовать**: УДД по дизайну исследования
  (шкалы приложения А2), предварительный УУР, вводную фразу из (направление, УУР), запрет слияния
  взрослых и детей / разных чисел / разного направления, «лишние» числа тезиса → `expert_additions`.
* **Статус выводится консервативно**: `verified` только если цитата найдена и все проверки
  пройдены; иначе `needs_review` или `unverified`. В подтверждённую часть черновика попадают только
  `verified` и карточки, подтверждённые экспертом. Остальное — в служебном приложении «Требует решения эксперта».

Рассмотренные и отклонённые альтернативы:

| Альтернатива | Почему не основная |
|---|---|
| Только LLM-проверка (self-consistency, N прогонов) | В N раз дороже; согласованная ошибка остаётся ошибкой; не проверяет наличие цитаты |
| Только строковая проверка цитаты | Цитата может быть настоящей, но не подтверждать формулировку (ТЗ прямо об этом) |
| NLI-модель (локальная) | Нет хороших русско-английских медицинских NLI; кросс-языковая пара «англ. цитата — рус. формулировка» |
| Ручная проверка всего | Масштаб: ~200 страниц КР; система должна сократить ручную работу до спорных мест |

## 3. Нормализация цитат (оговорённая заранее)

`textnorm.norm_hard`: Unicode NFKC → лигатуры (ﬁ→fi) → единые тире/кавычки/апострофы → нижний
регистр → удаление **всех** пробельных символов, дефисов, кавычек, `*`. Пробелы удаляются целиком,
потому что в PDF с выключкой по ширине пробелы и переносы расставлены произвольно; дефисы —
потому что «anti-\ninflammatory» в PDF и «anti-inflammatory» в цитате иначе не совпадут.

Совпадение: подстрока → `exact`; `rapidfuzz.partial_ratio` ≥ 90 → `fuzzy` (считается найденной);
75–90 → `partial` (на проверку); ниже — `not_found`. Если на указанной странице цитаты нет, ищем на
других страницах и на стыке соседних; найденная страница исправляет номер с пометкой.

**Найденная ошибка при разработке:** `page.get_text(sort=True)` в PyMuPDF сортирует строки по
координатам и перемешивает две колонки статьи. Модель «чинила» такие предложения при цитировании,
и 60% цитат не находились. После перехода на естественный порядок блоков — 99,5% цитат найдены.

## 4. Повторы и противоречия

LLM внутри раздела КР предлагает: кластеры (могут обосновывать один тезис), группы дубликатов
(перефразы одного утверждения), конфликты (одно вмешательство, одна группа — разное направление или
несовместимые числа). Затем `cluster.guard_duplicate` **запрещает** слияние, если различаются
возрастная группа (дети никогда не сливаются со взрослыми), направление утверждения или числовые
параметры. Отклонённые слияния сохраняются с причиной. Дубликаты не удаляются: `merged_into`
указывает на каноническую карточку, все источники остаются в тезисе. Противоречие показывается
вместе с обеими сторонами; система не выбирает сторону, решение эксперта фиксируется в журнале.

## 5. Тезисы, УДД и УУР

* Разделы 1.x и 7 — повествовательный текст со ссылками (как в реальных КР), без УДД/УУР.
* Разделы 2–6 — тезисы «Рекомендуется / Не рекомендуется …».
* **УДД** — из дизайна источника по таблицам 1–2 приложения А2 (диагностика / лечение,
  профилактика, реабилитация). Пересказ чужой работы (`secondary_citation`) не получает УДД статьи-пересказчика.
  Если дизайн не определён — УДД не присваивается, и система об этом сообщает.
* **УУР** — всегда предварительный (`uur_preliminary=true`): A — УДД 1 или ≥ 2 независимых
  источника УДД 2, всё согласовано; B — единственное исследование УДД 1–2, противоречия или
  согласованные УДД 3; C — остальное. Противоречия не дают A. Изменение экспертом фиксируется как его решение.
* Тезис, опирающийся только на результаты исследований (без явной рекомендации авторов), помечается:
  «предложен системой … требуется решение эксперта».
* Числа тезиса, отсутствующие в доказательствах, автоматически попадают в `expert_additions` с флагом.

## 6. Сохранение правок

Карточки и тезисы хранят два слоя: `auto` (машинный результат) и `override` (правки эксперта).
Повторная обработка пишет только в `auto`. Если новый `auto` отличается, а правка уже есть, он
кладётся в `pending_auto` и показывается эксперту для сравнения («Принять новую» / «Оставить мою»).
Если состав кластера сдвинулся и тезис получил новый идентификатор, новая автоверсия привязывается к
тезису эксперта с наибольшим числом общих карточек и тоже приходит как `pending_auto`. Тезисы с
правками, для которых новой версии нет совсем, не удаляются («осиротевшие»).
Решение «объединить / разъединить повтор» хранится отдельно от подтверждения карточки (`merge_lock`).
Все решения пишутся в `expert_edits`. Экспертный тезис создаётся без цитаты, с `provenance=manual`.

## 7. Ошибки и длинные документы

* Состояния документа: `done`, `done_empty` (обработан, утверждений нет), `partial`, `error`,
  `unsupported` (нет текстового слоя), `duplicate`.
* Ошибка API никогда не превращается в «утверждений не найдено»: фрагмент получает `error`, страницы —
  причину, документ — `partial`/`error`; уже полученные карточки остаются.
* Длинные документы: бюджет `max_pages_per_doc` (по умолчанию 60) на документ; страницы ранжируются
  по ключевым словам темы; пропущенные страницы видны в отчёте с причиной.
* Тестовый сбой: `KRGEN_FAIL_AFTER=N` — после N запросов «API» начинает отказывать.

## 8. Модель и ресурсы

* Claude Haiku 5.5 (`claude-haiku-5-5`; демо-корпус обработан на Haiku 4.5) через **Claude Agent SDK** с авторизацией **подпиской** Claude (OAuth-логин
  Claude Code CLI); `ANTHROPIC_API_KEY` принудительно удаляется из окружения, чтобы случайно не
  тарифицироваться по ключу. Инструменты агента отключены (`tools=[]`), пользовательские настройки не
  подгружаются (`setting_sources=[]`), ответ — JSON по схеме (`output_format`).
* Extended thinking по умолчанию выключен: с ним Haiku тратил 15–25 тыс. токенов и 2–4 минуты на
  фрагмент против 2–8 тыс. и ~40 с без него (≈ в 6 раз дешевле). Влияние на качество — предмет эксперимента.
* Стоимость в отчёте — эквивалент по прейскуранту API, который сообщает SDK; фактически
  расходуются лимиты подписки. Кэш-попадания стоят 0.
* Ответы кэшируются по (модель, версия промпта, бюджет размышлений, текст, схема) → повторная
  обработка воспроизводима и бесплатна; изменение промпта = новая версия = новый результат.

## 9. Ограничения

* OCR не выполняется: страницы без текстового слоя явно помечаются необработанными.
* Таблицы и рисунки извлекаются только как текст PDF; числа из таблиц модель часто не цитирует дословно
  (такие карточки уходят на проверку).
* Определение дизайна исследования — LLM по тексту первых страниц (с цитатой-обоснованием);
  ошибка дизайна → ошибка УДД.
* Оценка противоречий — внутри раздела КР; противоречия между разделами не ищутся.
* LLM-рецензент того же семейства моделей, что и генератор, — возможны согласованные ошибки;
  поэтому детерминированные проверки и экспертное подтверждение обязательны.
